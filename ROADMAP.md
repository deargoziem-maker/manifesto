# Roadmap: from MVP to a research-grade product

The site works fully on its own right now — quiz, candidate directory, and the
President game all run client-side with no backend required. This document
captures the fuller product vision (persistent data, analytics, an admin
dashboard) discussed for later, so it doesn't need to be re-decided from
scratch when you're ready to build it.

**Nothing below is required to launch.** Some of it already exists in the repo,
dormant and harmless — the frontend never depends on it being configured.

## What already exists, dormant

From an earlier pass at Phase 1, the repo already contains:

- `supabase/migrations/0001_init_schema.sql` — full Postgres schema: anonymous
  participants, sessions, a stable question/answer catalogue, per-decision
  responses, Compass and President results, optional demographics, and an
  event log.
- `supabase/migrations/0002_seed_questions.sql` — seeds that schema from the
  quiz/game content itself (generated by `scripts/gen_seed.py`, not hand-typed).
- `api/track.js`, `api/counter.js` — Vercel serverless functions that would
  write to that schema, using a Supabase service-role key that's never
  exposed to the browser.
- A small client-side tracking module in `index.html` (anonymous participant
  id, session ids, response-time capture) already wired into the quiz and
  game's existing event handlers — `pick()`, `play()`, `finish()`,
  `endGame()`, etc. Every call is fire-and-forget and fails silently if no
  backend is configured, which is the state today.
- An optional PostHog loader in `index.html`, inert until a project key is
  pasted in.

**To switch this on later**: create a Supabase project, run the two migration
files, and set `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` in Vercel's env
vars. See `README.md` → "Backend setup". No code changes needed.

## Why you'd eventually want this

Right now there's no way to know how many people used the site, where they
came from, what they answered, or what they did with the presidency — every
result lives only in the visitor's own browser and vanishes when they close
the tab. The features below turn the prototype into something you can learn
from: real usage numbers, a public "X Nigerians have taken this" counter, and
the actual distribution of political positions and governing choices across
everyone who's played.

## Remaining work, roughly in order

### 1. Get the dormant backend live
Create the Supabase project, run the migrations, set the env vars. Confirm
end-to-end: a real browser session produces real rows in `responses`,
`compass_results`, `president_results`.

### 2. Optional demographics step
A short, skippable step after someone sees their result — age range, gender,
state, Nigeria/diaspora. Table (`demographics`) already exists; needs the UI
and the explicit "this is optional" framing.

### 3. Privacy disclosure
A short, plain-language note (not a legal wall) covering: responses are
analysed in aggregate, individual political responses aren't publicly
identifiable, demographics are optional, we don't sell individual-level data.
Plus a placeholder `/privacy` page for the fuller policy.

### 4. Public completion counter
`api/counter.js` already computes this; it just needs a small UI element on
the landing page ("12,483 Nigerians have taken this") and `COUNTER_ENABLED=true`
once the number is worth showing.

### 5. Admin dashboard
A protected internal page: participant/session counts, completion and share
rates, per-question response breakdowns (using the stable codes), archetype
and President-outcome distributions, filterable by demographics where
available. Needs its own `/api/admin/*` endpoints behind a bearer token
(`ADMIN_TOKEN`), separate from the public tracking endpoint.

### 6. CSV export
Admin-only export of participants, sessions, responses, and results, joined
back to the stable question/answer codes for clean analysis.

### 7. Basic anti-bot / duplicate detection
The schema already has `is_suspected_bot` / `is_duplicate_candidate` flags on
`participants` and `sessions`. Needs the actual detection logic (rate
limiting, repeated-pattern detection) — flagging only, never auto-deleting.

### 8. PostHog (optional)
Paste a project key into `POSTHOG_KEY` in `index.html` to get funnel/product
analytics (landing → quiz start → completion → share) without touching the
database. Political-response content never goes to PostHog by design — that
stays in our own tables.
